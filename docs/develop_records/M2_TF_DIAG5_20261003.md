# M2 TF DIAG5 / physical-sector repair, 2026-10-03

## Board evidence entering this revision

- DIAG4 routed timing is closed: SWNS `+0.659 ns`, STNS `0`, HWNS `+0.014 ns`, HTNS `0`, confidence `Routed`, STA coverage `99.53%`.
- DIAG4 routed area: `13133 / 19600 LUT (67.01%)`, `7227 / 19600 REG`, `10 / 64 BRAM9K`, `0 / 16 BRAM32K`, `8 / 29 DSP`.
- The four independent LEDs are active-high `LED1..LED4 = led[0..3]`.
- The separate eight dual-color LED row uses the DIG cathodes as `LED6..LED13 = diag_led_n[0..7]`, active-low. Board observation after yellow -> red: physical `LED6` and `LED10` on, therefore the diagnostic byte is `0x11` (bits 0 and 4). Four-LED row: LED4 on, LED2 blinking, LED1 off; this is consistent with a latched media fault plus periodic rescan and no valid catalog.
- `0x11` is emitted only when `m2_real_media_service` is in FAT/catalog `SCAN` and its sector provider raises `sector_error`. The failure is therefore before BMP decode, framebuffer CDC and SDRAM display data.

## Root-cause candidate repaired

`sd_reader.make_cmd()` previously emitted CMD17 as:

```verilog
{8'h51, arg, 8'h00}
```

The final bit of an SD SPI command frame is the mandatory end bit and must be `1` even when CRC7 checking is disabled. The old `0x00` final byte therefore creates an invalid physical command frame. The simulation card models decoded the command index/argument but did not validate this end bit, allowing the production CMD17 framing bug to pass modeled-card regression.

DIAG5 changes CMD17's final byte to `8'h01`. Existing CMD0/CMD8/CMD55/ACMD41 bytes already end in `1`.

## Diagnostic refinement

The public media-service code remains compatible (`0x11` scan sector failure / `0x14` load sector failure), but the physical reader now exports a small sticky detail byte that the top latches at the same failure edge and displays on the eight-LED row:

| Byte | Physical-SD failure stage |
|---|---|
| `0x41` | CMD0 response/acceptance |
| `0x42` | CMD8 response/echo |
| `0x43` | CMD55 response |
| `0x44` | ACMD41 readiness/poll terminal failure |
| `0x45` | CMD17 R1 response/rejection |
| `0x46` | CMD17 data-token timeout/error |
| `0x47` | byte-engine handshake timeout |
| `0x48` | reader reported success but provider did not capture exactly 512 bytes |
| `0x4F` | reader failed without a more specific detail |

CMD55 is now explicitly required to return idle R1 `0x01` during initialization before ACMD41 is issued.

The bit-level modeled-card tests and the byte-level `tb_sd_reader` now assert that every six-byte SD command has `command[5][0] == 1`. This closes the exact simulation coverage hole that allowed CMD17 `...00` through.

## LED interpretation

Eight-LED row, with SW6 selecting LED supply:

- LED6 = bit0 / DIG0
- LED7 = bit1 / DIG1
- LED8 = bit2 / DIG2
- LED9 = bit3 / DIG3
- LED10 = bit4 / DIG4
- LED11 = bit5 / DIG5
- LED12 = bit6 / DIG6
- LED13 = bit7 / DIG7

No-fault build marker remains `0x81` -> LED6 + LED13. On a physical-sector error, the row shows the detailed `0x4x` code above. Four-LED meanings remain catalog / busy / completed-frame-ready / fault; LED3 is now additionally gated by `media_succeeded` so a pre-media display cannot be misread as a completed frame.

## Board confirmation after DIAG5

DIAG5 has now produced the first real-card image on hardware. With the TF card inserted, programming/reset first shows the yellow load page and then the actual 640×480 BMP. Reset with no card shows the red fault page; inserting the card and resetting again restores normal image output. This upgrades the CMD17/end-bit repair from a candidate root cause to **board-confirmed functional repair** for the tested card/profile.

After the successful first display, the board was observed with the eight-LED row showing physical LED6+LED7+LED9+LED10+LED11, i.e. `0x3B`, and the four-LED fault indicator still asserted. Code review found that the standalone top re-issued `OPEN(0)` after every successful `media_done`, so the first good framebuffer could remain visible while a later unnecessary reload faulted. The follow-up Master-control package therefore makes standalone image-0 load one-shot and gives the remote control plane ownership after link discovery.
