# 06 · “播放视频”的工程可行性与设计

> 结论先行：**EG4S20 无法解码压缩视频（H.264/HEVC/MP4/JPEG 视频），但可做“预转帧序列的流式视频播放”。**
> 具体能到什么程度，由 SD 卡读取带宽决定。下面是量化分析、格式设计与推荐档位。

## 1. 为什么“压缩视频解码”不可行

- EG4S20BG256 **没有视频硬解码器**（无 H.264/HEVC/JPEG 硬核）。
- 资源 19,600 LUT——要纯逻辑做一个 H.264 解码器，规模通常需要数十万级 LUT + 大量内存，**完全放不下**。
- 赛题红线**禁止外部处理器（MCU/CPU）**做辅助控制或算法预处理，等于堵死“外挂解码芯片”这条捷径。
- 因此“视频”只能用**PC 端离线转帧**（把 MP4/MOV 转成原始像素帧序列），FPGA 只负责**读帧→缓存→显示**。

> 这并不违反红线：与官方 `lab_ex_5` 播放 BMP 同理——图片内容由外部制作，FPGA 只做“解析+显示”这一 FPGA 擅长的处理。

## 2. 可行的三种“视频/动画”形态

| 形态 | 实现 | 可行性 | 建议 |
|---|---|---|---|
| A. 预转帧序列流式播放 | PC 把视频转成 `.vseq` 原始帧序列，FPGA 从 SD 读入并顺序显示 | ✅（受带宽限制，选低分辨率/中低帧率） | **主路线** |
| B. FPGA 实时生成动画/图形 | 用逻辑实时生成滚动字幕、动画、动态图形、进度条等 | ✅ 完全可行、无带宽瓶颈 | 补充，用于稳定演示 |
| C. 图片轮播（官方样例题） | BMP 逐张播放 + 转场 | ✅ 官方已验证 | 基础保底 |

## 3. 带宽预算是“视频”能做成什么样子的关键

### 3.1 每帧大小
| 格式 | 640×480 | 320×240 |
|---|---|---|
| RGB888（3B/像素） | 921,600 B | 230,400 B |
| RGB565（2B/像素） | 614,400 B | 153,600 B |

### 3.2 读取带宽需求 = 帧大小 × 帧率
| 流 | 每帧 | @20fps | @25fps | @30fps |
|---|---|---|---|---|
| 640×480 RGB888 | 921,600 B | 18.4 MB/s | 23.0 MB/s | 27.6 MB/s |
| 640×480 RGB565 | 614,400 B | 12.3 MB/s | 15.4 MB/s | 18.4 MB/s |
| 320×240 RGB565 | 153,600 B | 3.07 MB/s | 3.84 MB/s | 4.61 MB/s |
| 320×240 RGB888 | 230,400 B | 4.61 MB/s | 5.76 MB/s | 6.91 MB/s |

### 3.3 SD/TF 卡读取速率（近似）
| 模式 | 速率 |
|---|---|
| SPI 1-bit @25MHz | ≈3.125 MB/s（实际约 1.5–2.5 MB/s） |
| SPI 1-bit @50MHz | ≈6.25 MB/s（部分卡不支持） |
| SDIO 4-bit @25MHz | ≈12.5 MB/s |
| SDIO 4-bit @50MHz | ≈25 MB/s |

### 3.4 结论：可落地的档位
| 档位 | 视频规格 | 读取要求 | 风险 | 建议 |
|---|---|---|---|---|
| **推荐** | **320×240 RGB565 @ 30fps**（≈4.6 MB/s） | **SDIO 4-bit @25MHz（12.5 MB/s，余量大）** | 低 | ✅ 主推，显示时放大到 640×480 |
| 稳妥 | 320×240 RGB565 @ 20fps（≈3.1 MB/s） | SPI @25MHz（3.125，压线）需实测 | 中 | 备选（若 SDIO 难实现） |
| 进阶 | 640×480 RGB565 @ 25fps（≈15.4 MB/s） | SDIO 4-bit @~40MHz，余量小 | 高 | 不建议新手 |
| 不推荐 | 640×480 RGB888 @ 30fps（≈27.6 MB/s） | 超出本板读取能力 | 极高 | ❌ |

> **工程判断**：视频主档取 **320×240 RGB565 @ 30fps**，配合扩展③“自适应缩放”放大到 640×480 输出。
> 既保住“视频”卖点，又把读取带宽压到 SDIO 的 40% 以下，留足余量应对抖动。

## 4. 自定义视频容器格式 `.vseq`

为便于 FPGA 流式读取，定义单一容器文件（放 SD 卡根目录）：

```
.vseq 二进制布局（小端）
┌ Header（64 字节）：magic "VSEQ" | 版本 | width | height | bpp | fps | frame_count | 保留
└ Body：frame_count 个原始帧（每帧 width*height*bpp/8 字节，按 frame_size 对齐）
```

- 宽高建议 ≤320×240，bpp=16（RGB565），保证带宽与 SDRAM 余量。
- FPGA 先读 Header 拿到 `width/height/bpp/fps/frame_count`，再按帧顺序流式读入三帧缓冲。
- PC 端 `tools/` 提供 `video_to_vseq.py`（ffmpeg 或 OpenCV 转帧），一键生成 `.vseq`。

## 5. 帧缓存设计（视频三缓冲）

以 320×240 RGB565 为例，单帧 = 38,400 个 32bit word。
- 三帧缓冲 = 115,200 word（≈0.44 MB）→ 放 SDRAM，余量充足。
- **乒乓三缓冲**：SD 读一帧到“后备缓冲” → 显示端从“当前缓冲”读 → 缩放流水线输出。
- 显示端按 `fps` 用帧计数/计时器切换“当前缓冲”，实现平滑无撕裂。

> 显示流水线直接读小帧源图做“行缩放”，**不再**在 SDRAM 里另行存一份 640×480 输出帧，省带宽与存储。

## 6. 音画同步与音频可视化（扩展③⑤的交集）

- 音频：可为视频配一段预采样 PCM（`.wav`/`.pcm`，48kHz，放 SD），FPGA 按帧率时刻对齐播放（音画同步）；或先用 FPGA 合成测试音/背景音（更稳）。
- **音频可视化（扩展⑤）**：把音频包/采样数据做**幅度包络或简易 DFT/FFT**，在画面下方生成频谱/波形柱，叠加到视频画面。
  - 低频分辨率/FFT 在 19600 LUT 内可用 256 点/部分频点方案，**务必先仿真验证资源与时序**。

## 7. 分阶段落地节奏

| 阶段 | 视频相关内容 |
|---|---|
| P1 | 只跑通官方样例题（图片）；确认 SDIO 读卡速率（用工具测吞吐） |
| P2 | 定 `.vseq` 格式；实现 `vseq_reader` + 三帧缓冲；跑通“预转小视频”播放 |
| P3 | 接入缩放放大到 640×480；做转场/字幕（与视频叠加） |
| P4 | 加音频联动 + 音频可视化；压测稳定性 |

## 8. 风险与兜底

- **SD 读取带宽不足 → 卡顿/掉帧**：先降档（320×240@20fps 或 25fps），用“丢帧且不丢显示刷新”策略保证画面不花屏。
- **SDIO 控制器复杂**：若两周内调不通，退回 SPI + 低帧率，并把“视频”叙事改为“FPGA 实时动画 + 图影片段”。
- **资源不够**：视频 + 全部 5 项扩展可能超 19600 LUT；**以官方样例占用为基准**，优先保“基础四项 + 扩展①④③”。
